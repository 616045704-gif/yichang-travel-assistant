独立复核确认：

- `chat` 与 `trip` 共用经过核验的 HTTPS 服务地址，并仅在云函数中选择各自凭据；小程序前端及 demo 产物没有 Dify 地址、凭据、授权头或直接网络调用。
- 首次行程请求的代码映射为 `destination`、`people`、`totalBudgetCny`、`days`、`preferences`、`local_verified_facts`，同时保留内置 `query`；后续行程追问只复用该类会话。
- 云函数原子认领请求后先读取发布态 `places` 与 `place_contents`，再调用 Dify；非“记录不存在”的数据库错误不会被吞掉。
- `chat` 与 `trip` 按可信用户和类型使用不同会话槽位；重置、陈旧完成、旧缓存、并发认领和事务回滚均有自动化覆盖。
- blocking 调用的所有网络重试共享同一个 45 秒总截止时间；只重试网络失败及 HTTP 429、500、502、503、504，退避为 150 毫秒、400 毫秒，最多三次网络尝试。
- 同一逻辑请求的并发、缓存重放、失败冷却、最多两次上游逻辑调用及分钟/日配额均有覆盖。
- 对外错误与服务端诊断日志使用固定白名单分类，不输出上游详情或私有标识。
- 历史记录仅按当前用户查询，将问答与行程稳定倒序合并，并限制为最新 50 条。

## 阻断缺陷

### QA-BLOCK-01：`trip` 无法在 blocking 安全预算内完成

- 严重度：高，阶段阻断。
- 证据：两次真实云函数调用均在 45 秒返回安全超时；Dify 直接运行约需 67 秒。
- 影响：当前首次行程和行程调整不能稳定返回，双助手真实可用性不满足验收。
- 不接受的规避：把上游截止时间直接延长到 60 秒以上。既有实测表明小程序直接调用可能先断开，此时服务端仍可能保存成功并暂时阻止用户重试。
- 关闭条件：优化并重新发布 `trip` Chatflow，使典型及高分位耗时稳定低于 45 秒；随后各成功复验一次首次行程与后续调整，并保留超时异常路径。

### QA-BLOCK-02：已发布 `trip` 未声明本地资料输入

- 严重度：高，阶段阻断。
- 证据：已发布开始节点只显示五个行程字段，未显示可选文本变量 `local_verified_facts`。
- 影响：云函数虽然先查库并发送本地资料，已发布流程却不能可靠接收和优先消费它，数据库优先规则没有形成真实闭环。
- 关闭条件：在 `trip` 开始节点新增该可选文本变量，将其接入最终生成提示或等效后续节点并重新发布；使用非空发布态地点资料完成端到端复验。
