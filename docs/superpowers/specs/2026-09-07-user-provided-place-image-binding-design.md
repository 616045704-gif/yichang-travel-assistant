# 用户提供地点图片绑定设计

## 目标

将当前云存储中已上传、且已在本地清单登记为可用于本项目学习与面试演示的 25 组地点图片，精确绑定到同名地点的公开资料：每组第 1 张作为列表封面，第 2、3 张作为详情页图片段落。

## 范围

- 仅处理 `content/featured-place-images.json` 中 25 个稳定 `placeId`，覆盖景区、餐馆、文化馆/博物馆和露营地。
- 使用每条记录 `objectNames` 的第 1 项作为 `places.coverFileId`。
- 使用第 2、3 项对应的云存储 `cloud://` 文件 ID 追加为 `place_contents.sections` 的图片段落，图片替代文本使用地点名称与“图片 2”或“图片 3”。
- 原有文字段落必须保留，新增图片段落置于原有段落之后。
- 数据库中其他字段、其他 362 条地点、集合权限、环境变量、Dify 配置和云函数代码均不修改。

## 映射与写入规则

1. 以清单中 `placeId` 为唯一匹配键；云存储对象必须与 `objectNames` 完全同名。
2. 每个目标地点必须仍是 `published`，且分类必须与清单一致；每个地点必须已有同 ID 的 `place_contents` 文档。任一条件不满足时跳过该地点并报告，不写入猜测性的映射。
3. 所有 25 条通过预检查后，才执行字段级更新：
   - `places.coverFileId` 替换为第 1 张图片的文件 ID。
   - `place_contents.sections` 在保留原数组顺序的基础上追加第 2、3 张图片段落。
4. 操作必须可重跑：再次执行时先移除仅由本次绑定标记产生的同文件 ID 图片段落，再按固定顺序写入，避免重复图片。
5. 不保存临时 HTTPS 链接；前端继续由 `placeService` 按需解析 `cloud://` 文件 ID。

## 验收与回滚

- 写入前记录 25 条目标的 `coverFileId` 与 `sections` 快照，仅在当前受控会话内用于恢复。
- 写入后逐条确认：地点 ID、分类、发布状态、坐标和非图片文字段落未变化；封面与两个详情图片 ID 均匹配清单。
- 通过 `placeService` 的只读列表和详情调用抽查四个分类，确认列表有封面 URL、详情保留文字并包含两张图片 URL。
- 如任一目标写入或核验失败，恢复该目标的 `coverFileId` 与 `sections` 快照；不影响其他已核验目标。

## 安全与内容边界

- 图片权利依据沿用清单中的用户授权说明；不采集、下载或引入第三方图片。
- 不打印或提交云环境、存储桶、用户、密钥或临时访问链接等内部标识。
- 只通过受控 CloudBase 管理操作更新公共地点资料；不修改用户收藏、浏览、AI 记录或数据库权限。
