# 真实与模拟构建目录隔离设计

## 背景与根因

当前构建脚本会按 `demo` 或 `development` 两种模式生成小程序。两种模式此前都写入 `dist`：`demo` 包调用云函数 `aiService`，而 `development` 包会显示“模拟回答”。

2026-09-08 的界面改动验收显式执行了开发构建，并在 16:43 重写了 `dist`。开发者工具加载的正是该目录，因此真实 AI 包被替换为模拟包。这与 Dify、云函数、数据库和用户操作无关。

## 已确认设计

- `dist` 是唯一的真实体验包目录，只允许 `demo` 模式写入；微信开发者工具和体验版继续使用它。
- `dist-dev` 是开发模拟包目录，只允许 `development` 模式写入；它含模拟回答，仅用于界面交互开发。
- `npm run build` 与 `npm run build:demo` 继续生成 `dist`。
- `npm run build:dev` 和显式 `--mode=development` 改为生成 `dist-dev`，不再触碰 `dist`。
- 程序化构建的开发默认值保留，但它的输出也进入 `dist-dev`，让测试夹具和开发构建遵守同一隔离规则。
- 构建检查改为根据当前模式检查对应输出目录；生成的项目配置与云函数目录跟随各自输出目录。
- 开发指引明确：开发者工具只能导入 `dist`，不要导入 `dist-dev`。

## 非范围

- 不改 AI 页面问答逻辑、Dify 工作流、云函数、数据库、环境变量、密钥、AppID 或微信开发者工具账号设置。
- 不删除模拟能力；它仍可供前端界面调试使用。
- 不删除、移动或提交现有用户文件、备份目录或图片资料。

## 验收标准

1. `demo` 构建后，`dist` 包调用 `aiService`，没有“模拟回答”或“模拟行程”。
2. 随后运行 `development` 构建，不改变 `dist` 的上述真实 AI 内容，并在 `dist-dev` 生成模拟包。
3. 两个输出目录都通过适用的资源、包边界和项目配置检查。
4. 自动化测试覆盖目录选择和“开发构建不能覆盖真实包”的回归场景。
5. 开发者工具只需继续使用 `dist`；不需要任何云端、Dify 或密钥操作。
